libviprs benchmarks

How libviprs performs against itself: engine against engine, one archive against a directory tree, and both of those as releases go by.

Everything this site has published about performance so far has been libviprs against libvips, which answers a question about the other library rather than about this one. The interesting questions are internal. Which engine should you reach for, and at what size does that answer change? What does putting a whole pyramid in one archive cost or save against writing the classic tile tree, in bytes and in the sheer number of files a filesystem ends up holding? And when any of that moves, was it the code or the machine?

Every number below is generated from an archived run addressed by digest, and the raw rows are in history.json next to this page. Nothing here is typed in by hand, including the prose that quotes a figure. The libvips comparison has not gone anywhere: it is the same hand-written article it always was, at libviprs vs libvips.

Measured 2026-09-15 · run 20260915T021911Z-809ee8014d002518ce55edaceba698ca7a8b8a79-a7bac4a9

Three engines, the same pyramid, and where the memory goes.

All three build the same tiles from the same source and produce the same tile count, which the invariants below say exactly. Where they part company is how much of the image they are holding while they do it. At 12000x8400@256+c1, 2119 tiles, the monolithic engine peaks at 651.9 MB resident against streaming's 333.4 MB, a factor of 1.955, for wall times of 1062 ms against 1093 ms, 2.9% apart. The tracked working set underneath it is starker still: 288.4 MB against 27.47 MB.

These are three separate measurements. 0 of 16 groups in this run report the same peak resident set for every engine, which is what a sweep that measures each engine in its own child looks like. A sweep that reads one process-wide high-water mark reports the same number three times, and this one does not.

No cell here is gated, and none of them carries a chip. 288 of 288 cells are published as measured and not gated, and the method section lists every reason with a count against it. The numbers are real; what is missing is anything that could grade them.

144 of this run's rows arrived filed as replicates of a cell they are not. The run declares 512x360@256+c1 as the cell it measured twice, and a replicate is the same cell measured twice. These rows name different cells, at 1 thread and 8 threads, which share a tile count with their twins and are otherwise a separate arm of the experiment. The page reads them as the cells they say they are. Dropping them would have lost half of what this run measured, with nothing on the page to say so.

What the thread count costs in memory

Every row is the same image built twice, once on 1 thread and once on 8, with the peak resident set of each build beside the other. Read the bottom row: at the small end every engine is dominated by fixed setup, and a percentage there is mostly about the setup. At 12000x8400@256, monolithic and streaming do not move (+0.1%, -0.0%). mapreduce rises with the thread count (+4.6% at that size), and across every size it runs +0.0% to +8.1%. Throughput barely moves either way, which is in the table above: the thread count is buying memory here rather than speed.

  • monolithic holds the whole image, so the thread count changes nothing about what is resident.
  • streaming works a strip at a time, so its working set is bounded by the strip rather than by the thread count.
  • mapreduce keeps several strips in flight, which is what buys the parallelism and what it pays for in resident memory.

What this page does not measure.

HTTP, and object storage

Every read on this page is a local file read. PMTiles is designed to be range-requested off a static host or a bucket, which is where a single addressable archive pays for itself hardest, and none of that is measured here. The request counts in the full results are the closest thing on the page, and they are a count rather than a timing.

A cold page cache

Cold means a cold reader: a fresh process opening an artefact it has not opened. The kernel's page cache is whatever the preceding work left it, which is why the run records the page-cache state as warm-unknown rather than claiming to have dropped it. A genuinely cold cache is a different measurement and would need the host to cooperate.

macOS, Windows, or any filesystem but this one

One host, one filesystem, one architecture. The directory backend in particular is a measurement of how a specific filesystem handles tens of thousands of small files, and that is exactly the number that moves most between filesystems. The era rule above is what stops a run from a different machine being drawn on the same line as this one.

Other codecs

One encoder, at one setting, for every cell. Tile bytes drive both the output totals and the read work, so a different codec moves both, and nothing here says by how much.

The directory backend's request counts

PMTiles counts the requests a reader actually issues, because the reader is the thing being measured and it knows. The directory tree has no reader to count: its index work happens in the kernel, one path resolution at a time. So its request figures are declared by a model of what an HTTP client would have to ask for, they are labelled declared everywhere they appear, and they are not a measurement of anything that ran.

More than two thread counts

The engines sweep builds each image at one thread and at eight, and nothing in between. That is enough to say whether an engine trades memory for threads at all, and not enough to say what the curve looks like or where it stops paying.
